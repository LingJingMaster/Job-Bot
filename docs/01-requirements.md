# 需求与范围

## 1. 用户、场景与痛点

**目标用户**：中国大陆、正在使用 Boss 直聘找工作的个人（首位用户即项目负责人，应届/转岗均可）。

**场景**：用户在 Boss 上按关键词看到几十上百个岗位，要决定投哪些、简历怎么改。

**现有做法与痛点**（这些是**待用问卷验证的假设**，见 §5）：

1. 逐条点开 JD 阅读，筛选耗时；关键词搜索看不出“是否真的适合我”。
2. 对每个 JD 手改简历：容易遗漏关键要求，或为了贴合 JD 夸大经历（参与写成主导）。
3. 多版本简历、投了哪些岗位、用的哪个版本，缺少记录。
4. 通用大模型润色会编造数字与经历，且难以逐条核对。

**Job-Bot 要改善的**：缩短“筛选岗位 + 定制简历”的时间，同时保证简历每条事实可追溯到用户确认过的事实。

## 2. 范围

| 在范围内（课程版） | 不在范围内（v1 长期设计，不实现） |
|---|---|
| 简历解析、逐条事实确认 | 自动打招呼 / 发简历 / 批量投递 |
| Boss 只读采集 JD（登录后浏览器内采集）；粘贴/导入作为兜底 | 其他招聘平台自动化 |
| 岗位结构化、硬条件判定、匹配排序与解释 | 面试、Offer、复盘、通知、定时任务 |
| JD 定制简历：证据映射、追问、草稿、校验、导出 | 对话式任务入口、排除名单 |
| 申请状态手动记录（简单看板） | 多用户、认证体系、备份恢复演练 |
| 标注工具与评测脚本（支撑实验） | OCR 扫描件、云端部署 |

“真实平台”的含义：**JD 数据来自真实 Boss 页面，由真实登录会话获得**。投递动作由用户在平台上自己完成，系统只记录。

## 3. 需求清单

与 v1 编号对应关系：R01=F01，R02=F03，R03=F02，R04=F04，R05=F05，R06=F06 的人工部分，R07=F12 简化，R08 为新增。

| ID | 需求 | 输入 → 输出 | 必须满足的边界 |
|---|---|---|---|
| R01 | 简历导入与事实确认 | PDF/DOCX/TXT/MD → 候选事实列表（含原文定位）→ 用户逐条确认/修改/拒绝 → 确认版本 | 候选事实不得自动确认；解析失败保留原文件与错误；扫描件仅提示“暂不支持”；贡献强度（支持/参与/负责/推动/主导）与是否估算须显式记录 |
| R02 | 岗位采集 | Boss 登录会话中的浏览 → JobSnapshot；或粘贴 JD/导入 JSON → JobSnapshot | **只读**；单次运行条数、间隔有上限；遇登录失效/验证/异常响应立即停止并说明；来源标注 platform=boss / manual；同岗内容变化产生新快照 |
| R03 | 求职偏好 | 城市、薪资区间、学历/经验、岗位词、排除词 → Preference | 区分硬条件与软偏好；未知条件不当作“不满足”；保存版本 |
| R04 | 匹配排序与解释 | 确认档案版本 + 偏好 + 岗位集合 → 排序列表、分项得分、证据引用、缺口、未知项 | 硬条件 fail 不进入默认推荐但可查看原因；解释只引用已确认事实与 JD 原文；引用无效则退回模板解释；档案变更后旧结果标“旧版” |
| R05 | JD 定制简历 | 选定岗位 + 确认档案 → 要求–证据映射、≤5 个追问、简历草稿、校验结果、导出文件 | 不编造；追问答案先成为候选事实、经确认才可用；校验出无依据陈述则不可批准；不同岗位版本相互独立；导出文本可复制、中文无乱码 |
| R06 | 申请跟踪 | 用户手动更新 → 阶段、使用的材料版本、备注、时间线 | 阶段枚举见 03；不触发任何外部动作；更正需记录 |
| R07 | 数据管理 | 导出 / 清除 | 导出不含 Cookie 与 API Key；清除覆盖数据库、原始文件、向量缓存、LLM 缓存 |
| R08 | 评测支持 | 岗位池 → 盲标界面；评测脚本 → 指标与逐条结果 | 标注时不显示模型分数/排名；结果文件格式见 04 |

## 4. 用户流程

1. **首次**：配置 LLM（可跳过，见降级）→ 上传简历 → 核对候选事实并确认 → 填写偏好。
2. **采集**：点击“启动采集”→ 弹出受控浏览器 → 用户扫码登录并在 Boss 上搜索/点开岗位 → 系统逐个捕获 JD 并入库（或使用自动点击模式，见 02）→ 用户停止或达到上限。
3. **筛选**：在“岗位与匹配”页查看排序；点开某岗位看分项、证据、缺口；收藏/拒绝并选择原因。
4. **定制**：对选定岗位运行流水线 → 查看要求–证据表 → 回答追问 → 审阅草稿与校验结果 → 修改 → 批准 → 导出。
5. **投递与记录**：用户在 Boss 上自己投递，回到系统记录“已投递”及所用材料版本。

**降级路径**（须在界面说明原因）：

| 条件 | 可用 | 不可用 |
|---|---|---|
| 无 LLM Key | 简历手动录入事实、JD 粘贴、B0/B1 排序（B1 需本地模型）、手动材料编辑与规则校验 | 自动抽取、解释、草稿生成 |
| 采集器不可用 | 粘贴 JD / 导入 JSON | Boss 自动采集 |
| 无本地 embedding 模型 | B0 | B1/B2/B3 |

## 5. 成功标准

下列为**目标**，在实验前冻结；结果不达标也如实报告。

| ID | 指标 | 目标 | 度量 |
|---|---|---|---|
| S1 | 采集成功率：被点开的岗位中成功生成完整 JobSnapshot 的比例 | ≥ 90%（≥ 30 次点击的一次会话） | E0 |
| S2 | 排序：B3 或 B2 的 NDCG@10 高于 B0，硬条件误放行率不高于 B0 | 方向性目标，逐 profile 报告 | E1 |
| S3 | 材料：批准版本中无依据陈述为 0；校验器在注入伪造集上召回 | 终稿 0；召回 ≥ 0.8（目标） | E3、E5 |
| S4 | 效率：筛选 30 个 JD 的耗时较纯人工下降 | ≥ 50%（n 很小，仅作参考） | E4 |
| S5 | 完整运行：一次从采集到导出的端到端录屏，可复现 | 通过 | 演示脚本 |

**需求来源证据**（支撑评分“需求价值 15 分”）：

- 问卷/访谈：约 10 位有求职经历的同学，问题包括每份投递耗时、最大痛点、是否用过 AI 改简历、遇到什么问题。问卷题目和脱敏结果入 `eval/survey/`。
- 项目负责人自己的求职日志：筛选一次岗位列表的真实耗时（即 E4 的人工基线）。

## 6. 页面（Streamlit 多页）

| 页面 | 内容 | 关键操作 | 空态/错误 |
|---|---|---|---|
| 设置与状态 | LLM 提供方与模型、预算、采集器状态、数据目录、能力矩阵（可用/降级/不可用及原因） | 保存配置、连接诊断、清除数据 | 缺配置给可读提示；Key 仅显示掩码 |
| 简历与事实 | 上传、候选事实列表（原文定位）、状态、版本 | 确认/修改/拒绝/撤销 | 解析失败显示错误与原文件；撤销事实后列出受影响材料 |
| 岗位采集 | 启动/停止采集、运行记录（条数、成功/失败、停止原因）、粘贴 JD、导入 | 启动、停止、导入 | 登录失效/被拦截时显示停止原因并不重试 |
| 岗位与匹配 | 排序表（硬条件分组）、分项得分、证据与缺口、JD 原文、快照时间 | 运行匹配、收藏/拒绝、进入定制 | 无档案/无岗位时引导；旧版结果标识 |
| 材料工作台 | 要求–证据表、追问、草稿、Claim 校验、版本对比、导出 | 回答追问、编辑、重新校验、批准、导出 | 存在无依据陈述禁用“批准”；导出失败不丢文本 |
| 申请跟踪 | 看板、材料版本、备注 | 手动改阶段 | 拖动/修改不触发外部动作 |
| 标注与实验（研究模式） | 盲标队列、进度、一致性；运行评测的入口与结果链接 | 打分、跳过、复标 | 标注期间隐藏所有模型输出 |

跨页要求：中文标签；错误说明“发生了什么、数据是否保存、下一步”；长任务（采集、匹配、生成）显示进度并可中止；刷新后从数据库恢复状态。
