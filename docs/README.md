# Job-Bot 工程文档（课程版 v2）

版本：2.0　编写日期：2026-11-04　状态：设计基线，**尚无任何实现、实测结果或实验数据**。
截止：2026-11-18（《机器学习》期末项目）。团队：1 人（项目负责人）+ 若干协助编写代码/报告的人或 AI。

## 一句话定义

Job-Bot 是一个本地运行的 Web 工作台：**从 Boss 直聘只读采集真实 JD → 与用户已确认的简历事实做匹配排序 → 针对选定 JD 生成有证据约束的定制简历 → 人工确认后导出**。不向招聘平台发送任何内容。

## 与 v1 的关系

`archive-v1/` 是此前面向“可长期运营的完整产品”写的设计（14 个功能、40 个场景、PostgreSQL、Worker、审批/外部动作协议）。v2 是**两周可交付的课程切片**：

- 冲突时**以 v2 为准**。v1 只作为长期方向的参考，不是本次的交付要求。
- v1 中以下内容整体移出范围：外部动作审批与 unknown 状态机、面试/Offer/复盘、定时任务、对话式入口、排除名单、多用户与备份恢复。移出原因与恢复条件见 [07](07-sources-decisions.md) 的 ADR。
- v1 的下列原则被保留并写入 v2：事实底稿与生成文本分离、匹配分不是录用概率、无依据陈述不得批准、实验可重算、未实测不得宣称。

## 不可破坏的规则

1. **采集只读。** 代码中不得存在向招聘平台写入的路径（点击沟通/发送/上传、提交表单）。由测试 T07 静态检查。
2. **事实底稿与生成文本分离。** 只有 `confirmed` 事实可进入材料；材料中的事实性陈述必须挂到事实上。
3. **无依据陈述不得批准或导出终稿。** 疑点交用户处理，不得自动“修成看起来合理”。
4. **匹配分不是录用概率。** 界面与报告均不得如此表述；不基于姓名、性别、年龄、婚育等属性排序。
5. **所有 LLM 调用经统一网关**（缓存、预算、日志）。云端调用前明确哪些字段会发出。
6. **实验可重算。** 汇总指标必须能由逐条结果文件重新算出；测试集冻结后不再调参；不达标也如实报告，不删难例。
7. **未实测即标 `unverified`。** 文档中的数字（成功率、时延、指标）均为目标，不是结果。
8. **隐私与许可。** Cookie、API Key、简历原文、JD 原文不进入公开仓库；复用组件逐项登记来源、版本、许可证、用途。
9. **AI 参与可说明。** 使用生成式 AI 写代码/文档的环节需记录；提交者必须能解释自己提交的设计与代码。

## 状态词汇

`planned`（已计划）· `not_run`（未运行）· `passed` / `failed`（有证据）· `blocked`（被依赖阻塞）· `unverified`（外部事实未验证）。只有附带日期、提交号、输入摘要和结果文件，才能把 `planned` 改为 `passed`。

## 术语

- **事实（Fact）**：从简历抽取、经用户确认的一条陈述（经历、技能、成果）。
- **快照（JobSnapshot）**：某次采集到的 JD 内容，不可变；同一岗位内容变化产生新快照。
- **材料（Material）**：针对某 JD 生成的简历/话术版本，带逐条 Claim。
- **Claim**：材料中的一条事实性陈述及其支撑事实。
- **硬条件**：地点、学历、经验年限等可判定条件；结果为 pass / fail / needs_review。
- **池化标注**：把多个模型的 top-K 与随机样本合并后供人工打分，用于估计排序质量。
